# MFCL native backend prototype

Experimental Rust process. Download and ZIP staging operations write files to caller-specified locations. When configured, the launcher uses the native backend for supported checksum-verified downloads, Microsoft device and authorization-code login and refresh, offline UUID verification, supported instance enumeration and inheritance planning, asset-index parsing and hash inspection, standard-layout library classpath planning, batched Unix library hash inspection, launch-argument placeholder expansion, and Unix game process creation; most operations still use HMCLCore. The experimental instance inventory is not suitable for compatibility decisions: its manifest parsing only checks whether JSON is an object, not whether HMCL accepts the manifest, resolves inheritance, or recognizes Classic instances.

Repository refresh uses the separate `list_instance_dirs` operation to enumerate directory candidates when the native process is available. After Java parses the manifests, `find_invalid_inheritance` finds chains ending in a missing parent for both refresh and draft publication, while retaining cycles as the original implementation does. `plan_inheritance` supplies ordered chains for manifest resolution, `merge_manifest` applies inheritance field precedence, and native patch operations apply patches either in stable priority order or their original order, as required by the caller. These operations use opaque tokens referring to existing typed Java values; Java validates chain links, reconstructs the typed manifest and preserves raw JSON behavior. This avoids serializing unknown extension objects or credentials into the merge request. Java still validates instance IDs, recognizes Classic, parses manifest data and publishes the snapshot. Non-UTF-8 names, oversized results, invalid native responses or backend failures fall back to Java. This does not make the experimental `scan_instances` output a compatible repository snapshot. Disable these integrations with `-Dmfcl.native.instances.enabled=false`.

The opt-in `DefaultGameRepositoryDraftTest.liveVanillaInstallUsesNativeDownloads` integration test downloads the official 1.20.1 client and assets into a temporary directory. Set `MFCL_LIVE_GAME_INSTALL=1` and `MFCL_NATIVE_TEST_EXECUTABLE` to the compiled backend path to run it; set `MFCL_LIVE_GAME_LAUNCH=1` to also start and stop the isolated offline game with software rendering. `MFCL_LIVE_FABRIC_VERSION` or `MFCL_LIVE_QUILT_VERSION` optionally installs the chosen loader. For Fabric 0.15.11, `MFCL_LIVE_FABRIC_METADATA_FIXTURE=1` uses the bundled official metadata snapshot while dependency downloads remain live and direct. `MFCL_LIVE_GAME_JAVA` selects a Java 17 executable, defaulting to `/usr/bin/java`. An optional `MFCL_LIVE_CACHE_SEED` points to an existing test cache root; SHA-1 entries are independently verified before use. This test requires network access and, for launch, a working graphical display. It is excluded from ordinary offline test runs.

`plan_loader` reads Fabric, Legacy Fabric and Quilt loader metadata in Rust and selects the client main class, optional LaunchWrapper tweaker, ordered common/server libraries and loader coordinates. Java converts the selected library descriptors to the existing typed patch and performs dependency installation. Published top-level SHA-1 values are retained for libraries that do not already have explicit download metadata. Required vanilla files, loader libraries and Fabric-family API mod downloads now cause installation to fail when they cannot be downloaded, rather than silently leaving an incomplete instance. Unsupported or malformed metadata, oversized requests and native failures fall back to the original Java parser. Set `-Dmfcl.native.loaders.enabled=false` to disable this planning path. Offline differential fixtures include Fabric and Quilt metadata snapshots.

Build and test with `cargo test --manifest-path mfcl-native/Cargo.toml` and `cargo build --release --manifest-path mfcl-native/Cargo.toml`. The test suite uses only temporary fixture directories. No existing Minecraft data is needed.

## Protocol v1

The process reads one UTF-8 JSON request per line from stdin and returns one JSON response per line on stdout. Each request has `version: 1`, an `id`, a `method` and optional `params`. Responses repeat the id and contain either `result` or an `error` object with `code` and `message`. stderr is reserved for diagnostics. Requests above 1 MiB terminate the connection; manifests above 16 MiB are skipped with a warning.

Examples:

```json
{"version":1,"id":1,"method":"health"}
{"version":1,"id":2,"method":"sha256","params":{"path":"/tmp/example"}}
{"version":1,"id":3,"method":"scan_instances","params":{"game_directory":"/tmp/test-minecraft"}}
{"version":1,"id":4,"method":"offline_profile","params":{"username":"Steve"}}
```

`scan_instances` is a partial inventory, not a replacement for the Java repository. It enumerates `versions/`, chooses the conventional manifest or the only `.json`, and returns id, manifest path, manifest id and warnings. It does not follow inherited versions, validate the complete manifest schema, inspect game files, or generate an HMCL repository snapshot. Authentication requests and responses contain secrets; never put them in command-line arguments or logs. Only use trusted local callers; no caller authentication or sandbox is implemented.

Each native process handles requests sequentially. The Java download adapter exclusively borrows a worker for each transfer and may reuse it for subsequent requests; the Rust HTTP agent can reuse connections within that worker. At most 32 idle workers are retained, and workers idle for 30 seconds are reaped. Cancellation, protocol failures and executable replacement discard the affected worker. Download and library-hash requests can emit progress events; their Java adapters monitor cancellation and terminate the affected child. General-purpose multiplexing, broader crash recovery and cross-platform verification remain future work.

Modrinth exports can calculate SHA-1 and SHA-512 in one Rust file pass using a reusable worker. Stable Unix file identity is checked during hashing and rechecked by the Java caller; unsupported files fall back to Java. Disable this integration with `-Dmfcl.native.modpack.enabled=false`. For SHA-512 downloads, Rust verifies the declared digest before publishing its staging file; Java checks the digest again before final publication and supports checksum-based caching. Eligible SHA-512 transfers can use parallel ranges and checksum-addressed checkpoints, with a separate namespace from SHA-1. Older native backends fall back to Java. Existing destination files retain the prior skip behavior; modpack orchestration remains Java-owned.

Modpack override installation can also stage only the requested ZIP subtree through Rust. Java checks the staged entries and retains the existing filters, update rules and final file publication; unsupported archive paths, links, older backends or changed source archives use Java extraction. The modpack integration is enabled by default and follows `-Dmfcl.native.modpack.enabled=false` as well as the existing `-Dmfcl.native.natives.extract.enabled=false` extraction switch. Local update fixtures cover multiple override roots and user changes; real modpack archives have not been verified.

Initial JVM memory and ordinary argument defaults, as well as platform, game-proxy, generated optimization and Java-version defaults, can be selected in Rust using the current command and externally loaded JVM options. Platform and optimization choices are grouped after launcher-specific extensions. Game proxy options apply to the game process and do not change direct-only file downloads. Existing script-quoting modes are retained. Arguments are passed through one-shot process stdin because they may contain credentials. Unsupported values and backend failures retain Java generation; `-Dmfcl.native.launch.enabled=false` disables this path. Other JVM and complete command construction remain Java-owned. Both planners were exercised by an isolated offline Minecraft 1.20.1 launch to block-atlas initialization; other versions and platforms remain unverified.

Legacy Forge-family BootstrapLauncher ignore lists can be rewritten in a single native request using the ordered library classpath. Nonstandard paths or unsupported backends retain the Java rewrite; this uses the same `mfcl.native.launch.enabled` switch. Local fixtures compare the native and Java results, but this latest path has not yet been exercised against an actual legacy Forge version.

When recording a modpack's override configuration, Rust can hash the selected ZIP entries in one request. Java selects entries in its existing tree order and checks that the archive identity is stable across the native request. Duplicate names, unsupported archives, unavailable file identity or native failures retain the Java reader. This operation follows `-Dmfcl.native.modpack.enabled=false`.

Microsoft session validation and complete-profile reads can use a native read-only profile request, with Java preserving profile JSON validation and each caller's original text decoding. Public Mojang profile properties for Microsoft accounts also use native Yggdrasil-compatible transport and parsing when supported. HTTP 404 and redirects use the original Java path, including the license and missing-profile checks; transport failures can also be retried there. Direct JVM routes and standard networking settings are required, and `-Dmfcl.native.microsoft.enabled=false` disables these paths. JVM and Rust TLS trust roots can differ, and programmatically changed SSL contexts may not always be detected. Tests use synthetic responses; actual account interoperability remains unverified.

The cache repository supports SHA-1, SHA-256, SHA-512 and MD5 keys, and can verify cached files and restore candidates of at least 1 MiB with Rust. The same worker also computes SHA-1 for large remote-cache sources, timestamp rechecks and libraries without published digests. These digests match upstream metadata and do not authenticate it. Smaller files stay on Java to avoid per-file process communication overhead. Compatible large cache writes on Linux, including game libraries, can also be copied and verified by a reusable Rust worker into a private stage. Java rechecks the source identity, checks owner and group, preserves basic times and POSIX permissions, and publishes the staged file. Existing targets, special permission bits, extended attributes, ACLs, changed sources, other operating systems or native failures retain the existing Java copy. `-Dmfcl.native.cache.enabled=false` disables these paths. Final publication and cache indexing remain Java-owned.

Mojang Java runtime list selection uses a reusable Rust worker for canonical indexes, preserving candidate order and version matching; ambiguous or unsupported metadata falls back to Java. Mojang Java runtime installation checks manifest paths and link relationships before scheduling writes. Rust supplies a bounded lexical plan where supported, while Java checks normalized paths and existing symlink components. This preflight does not prevent a concurrent process from changing the filesystem afterward. Current official Linux, Windows and macOS Java 17 manifest shapes were checked on Linux. Compatible existing files can also be batch-checked through Rust, with identity rechecked before accepting an observation. On Linux, compatible LZMA files can be decoded by a reusable Rust worker into a private stage with a 128 MiB dictionary limit, an exact output-size bound and SHA-1 verification; Java independently verifies and publishes the result. Unsupported files, extended attributes, other platforms or native failures retain Java decompression. Native integrations are enabled by default and can be disabled with `-Dmfcl.native.java.enabled=false`. Canonical runtime manifests are parsed by Rust in original entry order, with unsupported shapes falling back to Java. On Linux, compatible runtime directories and symbolic links are created in Rust after Java and Rust path preflight; unsupported inputs fall back before mutation, while a failed mutating request is not replayed. Java retains download scheduling and final installation. An isolated direct-download installation of the official Linux Java 17.0.15 runtime exercised native list and manifest parsing, tree preparation and LZMA staging; its installed Java executable successfully ran `-version`. Other platforms and versions remain unverified.

The LZMA decoder uses `lzma-rs` and its `byteorder`, `crc` and `crc-catalog` dependencies under their MIT license options; callback token generation uses `getrandom` under its MIT option. Their license texts are in `mfcl-native/licenses` and are included in native-bundled launcher JARs under `META-INF/mfcl-native-licenses`.

## Launcher health-check integration

By default Gradle builds and embeds the current platform's Rust backend in the launcher JAR. At startup, the launcher asynchronously extracts the matching resource into the isolated launcher home under `native/`, reuses it only when its SHA-256 matches, checks its health, and enables supported native operations. The hash checks cache integrity; it is not a code signature. The process receives no account or game data during the health check. Until asynchronous discovery finishes, operations use their existing Java paths. If the resource is unavailable or fails validation, Java paths remain available.

`-Dmfcl.native.path=/absolute/path/to/mfcl-native` selects an explicit executable and prevents automatic discovery; an explicitly empty path also prevents discovery. `-Dmfcl.native.bundle.enabled=false` disables runtime discovery. For a Java-only development build, use `-Pmfcl.native.bundle=false`; the default build requires Cargo and the installed Rust target matching the build platform. Gradle `--offline` does not itself make Cargo offline; set `CARGO_NET_OFFLINE=true` when needed. The current build has been tested on Linux x86-64; other bundled targets require their own platform verification.

Native downloads, asset-index parsing, argument expansion, Microsoft authentication and native process creation can be disabled independently using `mfcl.native.download.enabled`, `mfcl.native.assets.enabled`, `mfcl.native.arguments.enabled`, `mfcl.native.microsoft.enabled` and `mfcl.native.launch.enabled` set to `false`. Game installation and most launch-command generation still use Java; on supported Unix systems, monitored game processes can be created through Rust.

## Experimental download

The `download` method requires `url`, `destination`, and `max_bytes` (1 to 1 GiB), and normally requires an expected `sha1`, `sha256`, `sha512` or `md5` digest. When `allow_unverified: true` is explicitly supplied without a digest, it stages bytes and returns their computed SHA-1. The Java integration uses this mode for other independently checked digests and for ordinary ETag-aware metadata, whose existing task context handles decoding, checks and publication. Metadata mode returns selected cache headers and supports conditional 304 responses. It supports HTTPS and up to five redirects to HTTPS destinations, without credentials in the URL or fragments. Redirects cannot downgrade HTTPS to HTTP. For local tests only, `allow_http_loopback: true` permits an HTTP URL with a numeric loopback IP. The destination parent must already exist. A temporary file is created alongside the destination and cleaned up on ordinary failure; publication fails if the destination exists. A process crash may leave a temporary file. Digests match upstream metadata and do not authenticate it. Progress events are available with `progress: true`. The native process does not implement general retry policies, mirrors, or file replacement; supported range transfers can retain completed checkpoints. The Java task adapter supplies cancellation, staging, validation, final replacement and cache handling, and falls back to Java for unsupported or failed cases.

`offline_profile` calculates the name-based offline UUID; it does not implement account login, skin support, Microsoft authentication or session management.

The Java `NativeBackend` adapter also exposes an experimental `calculateOfflineUuid` method. It starts a short-lived child, checks the response envelope and username, and returns a UUID. When `mfcl.native.path` is configured, automatic offline UUID generation during account creation calls this method and falls back to Java on failure or mismatch; an explicitly specified UUID bypasses it.

When configured, `FileDownloadTask`, `GetTask` and `CacheFileTask` use `NativeTransfer` for eligible HTTPS downloads, including checksum-verified files and ETag-aware metadata. SHA-1 is checked during native transfer; other algorithms are checked by the existing Java file context before publication. It preserves the existing cache lookup, integrity handlers, final publication, cache insertion, progress and speed accounting. Redirects, API-key hosts, explicit per-candidate timeouts and failed native requests use the Java path. At the user's request, Rust downloads ignore environment proxy variables, and Java download connections and their redirects explicitly bypass JVM/system proxy selectors. Authentication and other non-download requests retain their existing proxy behavior. The child writes inside a dedicated staging directory that Java removes after exit or cancellation. An abrupt launcher crash may leave staging files.

For SHA-1-, SHA-256-, SHA-512- or MD5-verified downloads of at least 1 MiB from servers advertising byte ranges, the adapter can use four direct range requests. At most eight files use ranges concurrently; additional transfers remain serial. Completed chunks are stored by checksum in the launcher's `cache/native-resume-v1` directory and may be reused after cancellation or restart. A per-checksum file lock prevents concurrent workers from modifying the same checkpoint; a busy or unsupported lock uses an isolated transfer. Each range and its declared offsets are checked, and the combined file must match its expected digest before publication. A rejected or malformed range response triggers a fresh serial request; corrupt checkpoints are discarded. Completed checkpoints are removed after success, while interrupted checkpoints remain available for a later attempt. Set `-Dmfcl.native.download.parallel.enabled=false` to disable range transfer or `-Dmfcl.native.download.resume.enabled=false` to disable persistent checkpoints. Both are enabled by default. Building the Rust backend requires Rust 1.89 or newer.

## Experimental ZIP staging

`extract_zip` accepts `archive` and `staging_parent` paths. It extracts into a newly created `.mfcl-extract-*` directory beneath the existing parent and returns that directory. This is a staging primitive, not a Minecraft installer: the caller owns the successful staging directory and must clean it up or incorporate it into a separately validated installation. Normal errors remove the staging directory; abrupt termination may leave it behind. The extractor rejects traversal, symlinks and other special files, conflicting paths, invalid ZIP data, more than 20,000 entries, files larger than 1 GiB, and more than 2 GiB of uncompressed data. It has not been validated on all platforms or against the full set of Minecraft modpack formats.

The Java adapter verifies the returned staging directory is directly inside the requested parent. The launcher uses this staging operation when extracting native libraries before game launch, while Java retains the existing entry filters, conflict handling, permissions and destination publication. It verifies the archive's file identity and entry paths and sizes before using staged files, cleans the temporary parent, and falls back to Java extraction for unsupported archives, filesystems or backend failures. Set `-Dmfcl.native.natives.extract.enabled=false` to disable this integration. Symlinks, incompatible ZIP paths and entries exceeding the native limits continue through the Java path. Other installers do not yet use the staging operation.

## Experimental Microsoft authentication

The process exposes legacy Microsoft authorization, token and exchange operations as well as combined authorization-session and refresh-session operations. When supported, the launcher uses the combined operations so intermediate Microsoft access tokens stay in Rust. The authorization-code operations accept the client ID, redirect URI and PKCE verifier; URL construction also accepts the callback state, while token exchange accepts the one-time authorization code. The legacy polling RPC is one request per call. With a capable backend, a dedicated Rust child handles polling intervals, pending/slow-down, expiry and Xbox/Minecraft exchange after the UI displays the code and acknowledges authorization. The device secret and intermediate Microsoft access token stay in that child, and cancellation terminates it without replay. Exchange performs Xbox Live, XSTS, Minecraft login, entitlement request, and profile lookup. Access and refresh tokens cross the local process protocol and must not be logged or written to command-line arguments. Only trusted local callers may access the process. Error messages exclude server-provided descriptions and credentials.

These operations are experimental. When an explicit or bundled native backend is available, Java device-code login, authorization-code token exchange and refresh use the native implementation by default if all authentication endpoints are direct according to the JVM proxy selector. Configured proxies or a backend missing required capabilities use the Java path before authentication starts; set `-Dmfcl.native.microsoft.enabled=false` to force the Java path. Rust uses its own TLS trust roots rather than the JVM trust store. A dedicated Rust loopback callback process generates state and PKCE verifier; Java independently checks the parsed callback fields and state and renders the localized response page. Before starting a browser flow, an older backend without the required capabilities falls back to Java; once a one-time authorization code may have been consumed, the flow is not automatically retried through Java. Tests cover an end-to-end authorization-code and refresh flow against a feature-gated numeric loopback mock, and a real device-authorization request with an initial pending poll; no real account sign-in was performed. Production builds ignore test endpoint overrides. Cross-platform callback interoperability, encrypted session persistence, detailed Xbox errors and live-service interoperability are not yet complete. Java Edition license/profile errors are distinguished. Do not use the prototype for production accounts.

## Experimental asset index planning

`plan_assets` parses an existing asset index into hash/size entries, preserving duplicate logical entries. It accepts up to 50,000 objects and a 64 MiB index, and requires standard 40-character hexadecimal SHA-1 hashes. When an explicit or bundled native backend is available, `GameAssetDownloadTask` uses this parser by default and falls back to Java on unsupported inputs or native failure. Existing Java code still checks files and constructs download tasks and cache updates. Cancellation terminates the native child. This is one part of resource installation, not a complete Rust game installer.

## Experimental Unix game process creation

With an explicit or bundled native backend available, the Java launcher probes the `launch_exec` capability and, for monitored game processes on Linux/BSD/macOS, starts the native executable in `--exec-child` mode. The launch command is sent over stdin; the Rust process replaces itself with the game process using Unix `exec`, preserving the PID, standard streams, inherited environment and working directory. The Java `ManagedProcess` continues to supervise the game. Use `-Dmfcl.native.launch.enabled=false` to retain Java process creation. Unsupported platforms, unmonitored inherited-I/O launches and older native binaries use Java.

The game command is assembled in Java, including Java selection, libraries and authentication rules. When configured, placeholder expansion for JVM, game, legacy, authentication and custom argument groups is performed by Rust; simple OS-name restrictions, ordered rule actions and feature conditions are also evaluated in Rust. Version or architecture regexes, combined OS/architecture names and non-ASCII OS names continue to be matched by Java. Unknown argument implementations and native errors fall back to the Java parser. Authentication values are sent through the child stdin and must not be logged. An exec failure after the request is sent is reported asynchronously through the child exit status and stderr instead of as a synchronous `ProcessBuilder.start()` error. An opt-in isolated Linux test installed vanilla 1.20.1, checked every indexed asset SHA-1, and launched an offline game with Java 17 and software rendering through Rust until the block atlas was created. Other real game versions, authentication modes and macOS/BSD behavior remain unverified.

## Experimental launch argument expansion

Quick-play, fullscreen, SOCKS game-proxy and graphics-backend arguments are planned in Rust when any are needed. The launcher keeps version detection and falls back to its Java implementation for invalid or unsupported address forms and native failures. SOCKS credentials pass over private child stdin and are not logged. Address and ordering tests compare representative IPv4, IPv6, Unicode and legacy cases with the Java parser; this does not configure the launcher's file-download proxy policy.

`expand_arguments` accepts ordered `groups` of strings and a `keys` object. It matches Java's sequential global replacement behavior, including nested placeholder values, skipped null arguments and Java's line-terminator handling. Limits on groups, arguments, placeholder matches and expanded bytes cause a Java fallback. The integration sends simple OS names and the current OS to Rust; complex restrictions are evaluated in Java before batching rules, feature conditions and argument groups for native selection and expansion. Local tests compare thousands of generated arguments against Java and exercise simulated platform combinations; real-game and platform coverage remain incomplete.

## Experimental library classpath planning

`plan_classpath` computes standard repository library paths, checks regular files, preserves order while removing duplicates, and applies the existing OptiFine installer ordering. The Java caller still evaluates platform and feature applicability and supplies the resolved library descriptors. Native planning is enabled when a backend is available; layouts that override `getLibraryFile`, unsupported inputs, or native failures fall back to the existing Java implementation. Tests compare generated library descriptors and custom, local, native and OptiFine cases with Java. Other platforms and real modpacks remain unverified.

The `auth-test-endpoints` Cargo feature exists only for isolated tests: it allows authentication service requests to be redirected to a numeric loopback HTTP origin. Default release builds do not enable the feature and ignore its environment variable. Never ship a binary built with this test feature.

Microsoft PNG skin uploads up to 8 MiB use the native backend when the capability and a direct authentication route are available. Other files and unsupported backends retain the Java path. A native upload is not replayed after it has been submitted, even if its response is lost. Multipart encoding and error handling have been tested only against local synthetic services; no real account was changed.

Direct HTTP(S) Yggdrasil authentication, refresh, validation and invalidation POST transport can use Rust, along with direct profile GET and supported skin PUT requests. Rust classifies login/refresh responses, checks the returned client token, decodes ordinary profile UUIDs and user-property entries, parses complete profiles, and decodes ordinary skin/cape texture maps. Unsupported values retain the exact JSON and use Java's existing type adapters. Credentials travel through one-shot child stdin and mutating requests are never replayed through Java after submission. Read-only profile redirects and failures return to Java's existing GET handling. JVM proxy selectors, cookies, authenticators, response caches, an explicitly configured trust store, nonstandard TLS factories or verifiers, API-key injection, unsupported endpoints or files, and older backends select Java before submission. Programmatically installed custom SSL contexts using the standard factory class cannot always be detected, and the Rust and JVM trust roots can differ. Response bodies are limited to 4 MiB before decompression and 16 MiB afterward; native skin uploads are limited to regular files up to 8 MiB. Set `-Dmfcl.native.yggdrasil.enabled=false` to disable this integration. Tests use local synthetic providers only; real third-party server and custom-trust interoperability remain unverified.

The vanilla client JAR is first downloaded into the existing content-addressed cache. Its SHA-1 is checked by both the native transfer and the Java cache context; only a later existing repository draft commit publishes it into an instance. Fixture tests cover cache hits, corruption, cancellation, cache failure and an isolated draft commit. Loader installation and the full installer remain primarily Java.

## Experimental installer processors

Forge-family profile data and processor literal expansion, plus Unix processor creation, use the native backend when available. Maven artifact paths are resolved by the existing repository layout before expansion; invalid native results fall back to Java. Plain profile data is still extracted by Java after expansion. Once a processor exec request has been sent, failures are reported instead of replaying the processor. Disable these integrations with `-Dmfcl.native.processors.enabled=false`. Java still orchestrates installation, verifies processor outputs and runs the processor tools themselves. Isolated installs of Minecraft 1.20.1 with Forge 47.2.0 and NeoForge 47.1.106, and Minecraft 1.20.2 with NeoForge 20.2.93, exercised processor expansion and launched offline games to block-atlas initialization; these fixtures do not establish compatibility with other versions or platforms.

Processor main-class and ordered classpath preparation now use Rust for supported JAR manifests and standard artifact layouts. Folded main-section attributes are supported; ambiguous ZIP entries, extra manifest sections, unsupported encodings and custom layouts fall back to Java. An isolated test-owned processor verified the native preparation and subprocess path; real installer coverage for this particular path remains pending.

Processor literal batches and file hash batches without progress callbacks reuse native workers after a capability handshake; workers are borrowed exclusively and are terminated on cancellation or protocol failure. Older backends use one-shot requests. Set `-Dmfcl.native.pool.enabled=false` to disable pooling for these pure requests. Authentication and launch-credential requests are not sent through this shared pool; the existing direct-download worker pool is controlled separately.

Forge-family processor outputs are inspected in Rust in batches when possible. Matching SHA-1 observations are used only after the file's path, size, timestamps and Unix identity are rechecked; changed files, mismatches and unsupported paths retain Java hashing and existing cleanup/error behavior. This does not yet replace installer orchestration or filesystem publication.

Forge and NeoForge processor option maps are planned together in Rust before sequential tasks are constructed, including empty flags, repeated keys, artifact paths and nullable variables. The adapter verifies option names and order and falls back to Java for unsupported inputs or backends. Local differential tests compare both Java parsers and mapping-task selection; an isolated Minecraft 1.20.1 / Forge 47.2.0 installation also exercised this path.

## Experimental library hash inspection

Legacy Forge-style checksum lists are also checked in Rust: the complete file SHA-1 is streamed first, then simple unsigned JARs can be checked against their embedded `checksums.sha1` entries. Files with ambiguous ZIP structures, data descriptors, `META-INF` files, unsupported encodings or changing identities fall back to the Java verifier. A native decision is accepted only after the file identity is rechecked. The feature follows `-Dmfcl.native.libraries.enabled=false`; it does not replace library installation or publication.

`check_files` streams SHA-1 calculations for a batch of existing files (`check_libraries` remains a compatibility alias). On Unix it returns a result only if the file size, modification/change timestamps, device and inode remain stable during reading. The Java installation task verifies that identity again before using the result, reports native batch progress as the first half of library verification, and retains its existing JAR ZIP and Forge additional-checksum checks. OptiFine and launcher-managed bootstrap files are excluded because the installation loop may modify them. Unsupported file systems, non-Unix builds, changed files, read errors, cancellation and native errors retain Java verification. The feature is enabled when a backend is available and can be disabled with `-Dmfcl.native.libraries.enabled=false`. This is not a replacement for the complete installer.

## Experimental asset hash inspection

For the standard asset layout, a combined Rust operation now parses the index and inspects existing objects in one pass, deduplicating repeated hashes. Java rechecks missing files and observed file identities before deciding whether to schedule downloads, and still owns cache updates and publication. Custom layouts, indexes with duplicate JSON keys, unsupported inputs and native errors retain the earlier Java workflow. Index and object paths retain symbolic-link traversal semantics. The existing asset parsing and hashing feature settings continue to control this path. Local task fixtures cover duplicates, cache behavior, symbolic links and files changed after planning; an isolated direct-download Minecraft 1.20.1 / Forge 47.2.0 installation exercised this path and launched to block-atlas initialization.

When a native backend is available and integrity checking is enabled, the asset task batches existing files for native SHA-1 inspection. Identical path/hash pairs are checked once while all logical entries remain in the installation list. Batches contain at most 500 unique files; a failed later batch leaves earlier verified observations usable and remaining entries fall back to Java. Java rechecks path, size, timestamps, device and inode before using each observation, and continues to handle missing files, cache insertion and download task creation. Progress and cancellation are supported. Disable this inspection with `-Dmfcl.native.assets.hash.enabled=false`; `mfcl.native.assets.enabled` independently controls index parsing. Non-Unix or unsupported metadata paths fall back to Java.

For launch argument selection, common OS version and architecture regexes are evaluated in Rust when Java and Rust syntax can be matched safely; common compound OS and architecture aliases are also matched in Rust; complex patterns and uncommon compound aliases retain Java matching.

Classpath planning and game-library installation use a reusable Rust worker for library rule selection before resolving paths and scheduling downloads; unsupported layouts and failed planning continue through the existing Java launcher path. An isolated Minecraft 1.20.1 install and offline launch exercised both selections and reached block-atlas initialization.

For classpath planning, Rust also determines whether each applicable library is native and selects its effective classifier in launcher-compatible descriptor order.

Native archive extraction selects applicable libraries and plans standard-layout archive paths in Rust; custom layouts fall back to Java, and archive filtering and publication remain managed by the existing launcher workflow.

Modrinth completion selects eligible client files and optional exclusions, plans canonical paths and checks SHA-512 syntax in Rust. Java independently checks paths and existing files and schedules integrity-verified downloads.

Modrinth update comparison uses Rust for old/new entry matching; Java preflights removal paths, and Linux removal uses Rust directory handles without following nested symlinks. Failed native removals are not replayed. Concurrent directory renames are not fully prevented.

Server-pack synchronization can use Rust batch SHA-1 observations for existing files, with Java identity checks and compatibility fallback before deciding whether to replace user content. Obsolete-file removal uses the same guarded Linux Rust path as Modrinth.

CurseForge completion uses Rust selection for metadata lookups, download candidates and checksum priority, with Java integrity-plan validation and fallback for changed hashes, non-ASCII blank-name checks and unsupported metadata.

Microsoft OAuth callbacks use a dedicated Rust loopback listener and parse ordinary query parameters in that isolated process; Java independently checks parsed fields and state and renders the response. Ambiguous queries use Java parsing, and credential-bearing requests do not enter the reusable worker pool. Native startup failures fall back before opening the browser; active callbacks are never replayed.

A one-shot Rust operation assembles expanded JVM, agent, main-class and game argument sections while retaining Java script-quoting flags; launch credentials are not sent through the reusable worker pool. A seeded offline Minecraft 1.20.1 launch exercised this operation and native archive planning through block-atlas initialization.

Canonical game-version catalogs can be parsed by Rust before Java merges unlisted versions and orders the results; noncanonical catalogs retain the Java parser.

Standard base-game installation manifests and canonical asset-index/download descriptors are decoded in Rust before Java applies the remaining nested type adapters to build the game patch; unusual or ambiguous manifests use the original Java parser.
